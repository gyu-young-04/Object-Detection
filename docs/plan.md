# 설계 계획서 — AI 기반 정리 가이드 어시스턴트

## 1. 프로젝트 개요

한 학기 동안 개인이 수행하는 설계프로젝트로, 스마트폰 카메라로 방을 촬영하면 AI가 물건을 탐지해 정리해야 할 물건과 목적지를 알려주고, 효율적인 정리 순서까지 제안하는 개인화 정리 가이드 시스템을 설계·구현한다.

## 2. 문제 정의 및 배경

1인가구 증가와 바쁜 현대인의 시간 부족으로 정리정돈에 어려움을 겪는 사람이 늘고 있음. 핵심 문제는 "정리가 절대적으로 불가능해서"가 아니라, 물건 수가 많을 때 반복되는 판단(결정 피로)과 "어디서부터 시작할지 모르는" 심리적 진입장벽임. 이 도구는 "모두에게 필수"가 아니라 결정 피로가 크거나 시작을 못 하는 상황에서 유효한 도구로 스코프를 명확히 한다.

방 내부 사진은 위치·소지품·생활패턴이 드러나는 민감 데이터이므로, 처리 방식 설계 시 프라이버시를 우선 고려한다.

## 3. 설계 과정에서의 AI 활용 및 트레이드오프 판단

| # | 설계 지점 | 검토한 대안 | 판단 근거 | 최종 선택 |
|---|---|---|---|---|
| 1 | 어질러짐 판단 방식 | baseline 변화탐지 vs 카테고리→목적지 규칙 | 변화탐지는 물체 재식별이 필요해 정확도 리스크 큼, cold-start 문제도 있음 | 카테고리→목적지 규칙 |
| 2 | 다각도 사진 처리 | 정밀 재식별(re-id) vs 탐지결과 단순 합집합 | re-id 실패 시 오탐 위험, 합집합은 실패해도 보수적으로만 작동 | 단순 합집합(같은 사진 내 중복은 IoU 병합, 다른 사진 간은 좌표비교 없이 결과를 그대로 합침) |
| 3 | 처리 위치 | 클라우드 API vs 로컬 오픈소스 모델 | 민감 이미지 외부 전송 문제, API 비용·토큰 이슈, 오프라인 데모 불가 | 로컬 오픈소스 모델 (구조적으로 온디바이스 전환 가능하게 설계) |
| 4 | 탐지 카테고리 확보 | 커스텀 클래스 파인튜닝 vs 오픈보캐뷸러리 탐지 | 파인튜닝은 라벨링 데이터 필요, 리스크 큼 | 오픈보캐뷸러리 탐지 (텍스트 프롬프트로 카테고리 지정, 학습 불필요) |
| 5 | 과거 위치 기억 | 인스턴스 단위 재식별 vs 카테고리 단위 개인화 | 동일 외형 물건(같은 티셔츠 2벌) 구분 불가라는 태생적 한계 존재 | 카테고리 단위 개인화 (클릭 예외 학습), 인스턴스 추적은 향후 과제 |
| 6 | 정리 순서 제시 | 물리적 적재 순서 추론(깊이/3D) vs 휴리스틱 정렬 | 3D 순서 추론은 단일 사진으로 리스크 큼 | 휴리스틱 정렬 (목적지 그룹핑 + 저노력 우선 + 밀집구역 우선) |
| 7 | 촬영 방식 | 오버헤드(하늘사진) vs 일반 각도 다각도 | 오버헤드는 촬영 자체가 어렵고, 탐지모델 학습데이터와도 안 맞아 정확도 저하 우려 | 눈높이 다각도 3~5장 |
| 8 | 재촬영 시점 | 실시간(치울 때마다) vs 라운드제(완료 후 1회) | 실시간은 마찰 큼, 라운드제는 처리된 물건이 자연히 사라져 별도 diff 로직 불필요 | 라운드제 |
| 9 | 동일 카테고리, 다른 목적지 | 서브카테고리 자동분류 vs 유저 선택(이번만/항상) | 자동분류(세탁여부 등 시각 판단)는 스코프 초과. 패턴이 있으면 카테고리를 더 세분화하도록 유도, 세분화가 어려우면 과거 목적지 히스토리를 기본값 뒤에 숨겨두고 필요시에만 펼쳐 보여줌 | 클릭 시 "이번만" / "항상" 선택지 제공 |
| 10 | 초기 목적지 설정 | 사전 설문 vs 기본 내장 규칙 + 클릭 보정 | 설문은 시작 전 추가 진입장벽 | 기본 내장 규칙, 틀린 것만 클릭 보정 |
| 11 | 고정 카테고리 외 물건("기타") 처리 | 미지원 vs 유저 정의 카테고리 확장 | 오픈보캐뷸러리 구조상 텍스트 프롬프트 추가는 비용이 거의 없음 | 유저 정의 카테고리 지원. 텍스트로 일반화 설명 가능한 물건에 한정 ("레고상자" O). 완전히 고유하고 설명 안 되는 물건은 인스턴스 재식별과 동일한 이유로 스코프 아웃 — 매 라운드 수동 태깅으로 fallback. 등록 직후 현재 사진으로 즉시 테스트해 탐지 여부를 바로 확인 |

## 4. 최종 목표

**MVP (필수 구현)**
- 다각도 사진(3~5장) → 오픈보캐뷸러리 탐지 → 합집합 통합
- 모드 선택: 전체 가이드 / 쓰레기만 / 영역 드래그
- 카테고리 목록: 정리대상 물건 15~20종 (옷, 쓰레기, 책/서류, 문구류, 그릇, 신발, 가방 등) — 가구·고정물 제외
- 유저 정의 카테고리 추가/관리 (텍스트로 설명 가능한 물건에 한정)
- 기본 규칙 테이블 + 유저별 예외(클릭 보정, 이번만/항상) 저장
- 색깔 오버레이 + 클릭 팝업(이유 설명, 템플릿 문장) + 체크리스트 뷰
- 휴리스틱 정리 순서 제시 (목적지 그룹핑/저노력 우선/밀집구역 우선)
- 라운드제 재촬영 플로우

**스트레치 목표**
- 경량화(양자화) 후 실기기(라즈베리파이/젯슨나노) 배포 및 지연시간·전력 측정
- (대안) PWA 전환 — 홈 화면 설치가 가능한 형태로 사용성 개선
- baseline 변화탐지 방식과의 정확도/실용성 비교 실험

**성과 발표 형태**: 실제 방 사진 라운드별 데모 + 정량 지표(탐지 정확도, 처리시간, 기본 카테고리 커버율) + (스트레치 달성 시) 온디바이스 비교표

측정 지표가 기대만큼 안 나올 경우:
- 정확도 낮음 → 카테고리 수 축소, 프롬프트 표현 개선, 모델 교체 시도
- 처리시간 느림 → 경량 모델(YOLO-World 등) 교체, 입력 해상도·카테고리 수 축소, GPU 활용 (실시간 처리가 아니라 사진당 수 초 대기는 허용되는 구조)
- 기본 카테고리 커버율 낮음 → 기타로 자주 빠지는 물건을 기본 카테고리 목록에 반영해 개선
- 그래도 개선 안 되면 결과와 원인을 있는 그대로 보고서에 기록

## 5. 시스템 아키텍처

```
[다각도 사진 3~5장 입력]
        |
[오픈보캐뷸러리 탐지모델 (로컬)] <- [기본 카테고리 + 유저 정의 카테고리 프롬프트]
        |                              ^
카테고리 + 좌표(바운딩박스)          [카테고리 관리 UI] (추가/수정/삭제, 등록 시 즉시 테스트)
        |
[탐지결과 합집합 통합 (같은 사진 내 IoU 병합 / 다른 사진 간 단순 합집합)]
        |
[카테고리 -> 목적지 규칙 테이블] <- [유저별 예외 규칙 DB]
        |
[모드별 필터링] (전체 / 쓰레기만 / 드래그 영역)
        |
[휴리스틱 정렬] (목적지 그룹핑 -> 저노력 우선 -> 밀집구역 우선)
        |
[색깔 오버레이 + 이유 설명 + 체크리스트 출력]
        |
[클릭 수정: 이번만 / 항상] -> 예외 DB 갱신
        |
[정리 진행 후 재촬영 (라운드 2, 3, ...)]
        |
(새로 드러난 물건만 자연스럽게 탐지됨 - 처리된 물건은 이미 사라짐)
        |
[탐지 결과 없을 때까지 반복 -> 완료]
```

**플랫폼**: 웹앱. 폰 브라우저(클라이언트) → 사용자 본인 소유 기기의 로컬 서버(백엔드, 파이썬) → 탐지 모델 실행 → 결과 반환. 외부 클라우드 업체 서버는 경유하지 않음. 각 사용자가 자신의 기기에서 직접 서버를 셀프 호스팅하는 구조라, 개발자가 운영하는 중앙 서버 자체가 없어 개발자도 사용자 데이터에 접근할 수 없음 (향후 다수 사용자를 위한 중앙 서버 방식으로 바뀔 경우 별도 프라이버시 설계가 추가로 필요).

## 7. 리스크 및 대응

| 리스크 | 대응 |
|---|---|
| 오픈보캐뷸러리 탐지 정확도 부족 (특히 작은 물건) | 카테고리 수를 좁히고, 일정 크기 이하 물건은 탐지 대상에서 명시적으로 제외 |
| 로컬 처리 속도 부족 | 경량 모델 교체, 해상도·카테고리 수 축소. 실시간이 아닌 비동기 구조라 기준 자체가 관대함 |
| 온디바이스 검증 실패/시간 부족 | 필수 목표에서 제외, "구조적으로 가능함"만 논리적으로 증명 |
| 의도적으로 배치된 물건도 오탐지 | "완벽한 정돈 판단이 아니라 일반적 기본 위치 제안"이라고 스코프 명시. 탐지 결과는 강제 지시가 아닌 기본 제안이며 최종 판단은 항상 사용자 |
| 다각도 사진 합집합 시 중복탐지 | IoU 임계값 기반 단순 병합(같은 사진 내)으로 스코프 제한, 다른 사진 간 중복은 허용 가능한 수준으로 감수 |
| 유저 정의 카테고리가 텍스트로 잘 탐지 안 됨 | 등록 즉시 테스트, 표현 재시도 유도, 그래도 안 되면 수동 태깅으로 fallback |
| 정식으로 안내할 만큼 정밀도가 나오는 카테고리가 적음 (2026-10-14 추가) | 카테고리별로 "참고용 → 정식" 등급제를 적용한다(#18). 정식 기준(검증용 사진의 정밀도 하한과 최소 건수)은 실험 전에 정한다. 정식이 아닌 카테고리는 점수 높은 순으로 "확인 필요"로 표시하고 사용자가 건너뛸 수 있게 한다 |
| 개선 실험(더미 정의, 프롬프트, 점수 기준 등)을 해도 정밀도가 오르지 않음 (2026-10-14 추가) | **10/29 판단 시점**: 개선 실험 후 유효 안내율과 애매 비율의 변화로 판단한다. 오르면 현재 범위를 유지하고, 오르지 않으면 정식 안내 범위를 좁히고 보고서를 "왜 되는 카테고리와 안 되는 카테고리가 있는가"를 분석하는 구조로 정리한다. 어느 경우에도 최소 프로토타입(사진 → 안내 → 수정 → 저장)을 함께 제출한다 |
| 실패 원인을 근거 없이 단정함 (2026-10-14 추가) | 원인은 가설로 표시하고, 조건을 바꿔 결과가 달라지는지 시험한 것만 원인으로 서술한다. 카테고리별 정밀도·재현율과 실패 유형 분류를 함께 제시한다 |
| 인터넷 샘플 사진 10장으로만 측정함 (2026-10-14 추가) | 본인 방의 폰 사진과 같은 방을 여러 방향에서 찍은 사진으로 추가 측정한다(방향 설정 단계에서는 샘플만 사용). 판정용과 검증용 사진을 분리한다 |

| 13 | 입력 해상도 | 800 vs 400 | 사진당 51초 → 17초(약 3배). 큰 덩어리는 비슷, 작은 물건은 놓침 | 400 |
| 14 | 결과 제시 | 전체 완료 후 vs 우선순위 순서로 점진 출력 | 옷이 있는 방은 첫 안내 약 2.8초 (전체 시간은 줄지 않음, 체감만 단축) | 점진 출력 |
| 15 | 포개진 박스 | 유지 vs 제거 | 정밀도 변화 없음(엄격 40.5% → 40.3%) | 제거 (화면 간결성) |
| 16 | 카테고리 충돌 | 둘 다 유지 / 점수 높은 쪽 / 우선순위 높은 쪽 | 점수 규칙은 오탐 11 → 8건, 우선순위 규칙은 쌍별로 1/5만 개선. 단 표본이 5쌍뿐 | 점수 높은 쪽 |
| 17 | 오탐 필터 | 큰 박스 제외, 카테고리별 최소 점수 | 가장 큰 박스가 36.8%라 불필요. 진짜와 오탐의 점수대가 겹쳐 보류 | 미적용 |
| 18 | 카테고리 확장 | 한 번에 확대 vs 등급제 | 카테고리가 늘면 시간·충돌이 늘 것으로 예상(미측정) | 참고용 → 정밀도 확인 → 정식 승격 (설계) |
| 19 | 제자리 물건 | baseline 비교 vs 건너뛰기 버튼 + 상황 문구 | 제자리 물건을 안내한 비율 약 13% | 건너뛰기 버튼(설계), 상황 문구 실험(이후) |

## 10. 구현·측정 현황 (2026-10-12 기준)

**구현됨**: 카테고리별 탐지, 박스 정리(중복·포개짐·카테고리 충돌), 카테고리 → 목적지 규칙과 목적지별 안내문, 목적지별 색 시각화, 점진 출력과 첫 결과 시간 측정, 방 단위 합집합, 정밀도 검수·계산 도구

**측정 결과** (작은 인터넷 사진 10장, 방 8곳)

| 항목 | 값 |
|---|---|
| 카테고리 1개당 시간 (해상도 400) | 약 2.7 ~ 3.1초 |
| 사진당 전체 시간 (6개) | 약 14 ~ 18초 (이 노트북에서 일시적으로 65 ~ 90초까지 느려진 적이 있음) |
| 첫 결과까지 (옷이 있는 방) | 약 2.8초 |
| 탐지 정밀도 | 엄격 40.5% / 관대 85.1% (판정 불확실 45%) |
| 이미 제자리인 물건을 안내한 비율 | 약 13% |
| 카테고리가 다른데 같은 위치인 박스 | 약 13% (5쌍) |

**한계**: 판정은 Claude가 했고 사용자 검수 전이다 / 재현율 미측정 / 사진이 작고 적다 / 속도 편차가 크다(같은 사진에서 72초, 34초, 14초가 관측됨. 측정은 반복해서 범위로 보고하고, 발표 데모는 결과를 미리 생성해둔다)

**미구현**: 개인화 저장(사용자 수정 반영), 웹 화면, 쓰레기·천류 등 카테고리 확장

## 11. 목표 재정리와 정확도 개선 계획 (2026-10-14 기준)

중간발표 직전에 측정 결과를 바탕으로 목표와 개선 방향을 다시 정리했다.

### 11.1 설계 판단 추가

| # | 설계 지점 | 검토한 대안 | 근거 | 선택 |
|---|---|---|---|---|
| 20 | 사용 대상 | 정리가 귀찮은 사람만 / 어디에 둘지 모르는 사람까지 | 목적지 추천은 규칙 표라 모델 학습이 필요 없고(`rules.py`에 이유 문장이 이미 있음), 탐지 정확도와 분리해서 평가할 수 있다 | 목적지와 이유(1~2개)를 함께 제시한다. 이유는 "일반적인 기준"으로 표시하고 단정하지 않는다. 추천 장소가 사용자 방에 없을 수 있어 시작할 때 "내 방의 보관 장소"를 선택하게 한다. 평가는 소규모 사용자의 추천 동의율로 한다 |
| 21 | 탐지 목표 | "보이는 모든 물건" / "정리 대상 카테고리의 보이는 물건" | 모든 물건은 6개 카테고리 모델로 불가능하고, 가려진 물건은 대상이 아니다 | 재현율의 분모를 "사진에 보이고, 정리 대상 카테고리에 속하고, 일정 크기 이상인 물건"으로 한정한다. 목표 90%는 현재 값(미측정)을 직접 세어 확인한 뒤 단계별로 정한다. 더 많이 찾으면 정밀도가 떨어지므로 정밀도와 함께 목표를 둔다 |
| 22 | 놓친 물건 기록 | 정리 중 등록 / 정리 후 기록 | 정리 중 등록은 흐름을 끊는다. 기록이 쌓이면 실사용 재현율의 근거가 된다(기록하지 않은 놓침은 빠지는 편향이 있음) | 정리 후 "놓친 물건이 있었나요?"를 한 번 묻고, 사용자 카테고리로 저장한 뒤 즉시 재탐지로 확인한다. 한글 이름을 모델(영어 프롬프트)이 이해하는지는 먼저 작은 실험으로 확인한다 |

### 11.2 정확도 개선 계획

현재 기준은 어지러운 방 8곳의 박스 74건이다 (O 20 / P 10 / A 33 / X 11, 판정은 Claude 기준, 사용자 검수 전).

모델이 달라지지 않는다고 가정하고 같은 판정 건수로 다시 계산한 시나리오다. 개선 효과의 예측이 아니라, 어디가 병목인지 보기 위한 계산이다.

| 가정 | 유효 안내율 (O 기준) |
|---|---|
| 현재 | 27% |
| 틀린 박스(X)를 전부 걸러냄 | 20/63 = 32% |
| X를 걸러내고 제자리(P)도 건너뜀 | 20/53 = 38% |
| 애매(A)의 절반이 정답으로 정리됨 | 36/74 = 49% |

- 오탐을 완벽히 없애도 크게 오르지 않으므로, 병목은 애매(A) 45%와 "박스 하나가 무엇인가"라는 정의다.
- 현실적인 기대 범위는 유효 안내율 40~55% 정도로 **추정**한다 (측정 전, 낮게 나올 수 있음).

개선 실험 순서 (한 번에 하나씩, 같은 사진·같은 판정 기준으로 비교):

1. 정답 기준 문서화와 사용자 직접 검수, 재현율 측정, 검증용 사진 분리
2. 단위를 "더미"로 정의 (더미 프롬프트, 판정 기준 변경)
3. 프롬프트 표현 변경 (`on the floor` 등 상황 문구)
4. 카테고리별 점수 기준
5. 후보를 이미지 분류 모델로 다시 확인하는 2단계 (오탐 필터. 위 계산상 효과가 작을 가능성이 있음)
6. 더 큰 모델이나 높은 해상도 (속도와 정확도의 교환)
7. 사용자 확인 UI (건너뛰기, "추천 / 확인 필요" 구간 표시)

실험 규칙: 성공 기준(예: 유효 안내율 몇 % 이상)은 실험 전에 정한다. 판정 기준을 바꿔서 숫자가 오른 경우는 모델이 좋아진 것이 아니므로 바꿨다는 사실과 이유를 반드시 기록한다. 같은 사진으로 판정과 개선을 함께 하면 과적합이 생기므로 검증용 사진을 따로 둔다.

### 11.3 이미 시도했으나 효과가 작았던 것

| 시도 | 결과 |
|---|---|
| 점수 기준 올리기 (0.30 → 0.40) | 엄격 정밀도 40.5% → 64.7%, 틀린 박스 11 → 3건. 대신 박스가 74 → 17건(23%), 진짜 필요한 물건(O)은 9/20만 남음. 점수대가 겹쳐 깔끔히 가르지 못함 |
| 점수 높은 것부터 확정하고 그 박스를 지운 뒤 재탐지 (블러 / 평균색, 10장) | 새로 잡힌 박스 11건(블러)·8건(평균색)이 모두 점수 0.30~0.33의 경계선. 눈으로 본 8건 중 맞아 보이는 건 2건. 기존 박스 16건(22%) 사라짐, 시간 약 3배 |

두 실험은 임시 스크립트로 측정했고 저장소 기록(devlog, 코드)은 이후 반영한다. 사라진 박스의 정답 여부와 새 박스의 정식 판정은 하지 못했다.
